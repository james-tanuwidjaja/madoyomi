# Madoyomi app (Tauri 2 + Vue 3)

Desktop shell and UI. See [../docs/PLAN.md](../docs/PLAN.md) for the architecture and [../docs/phases/](../docs/phases/) for the phases: the screens are [Phase 3](../docs/phases/phase-3-frontend-mvp.md)'s, playback [Phase 4](../docs/phases/phase-4-playback.md)'s, the manga reader [Phase 5](../docs/phases/phase-5-manga-reader.md)'s (done: the paged, double-page and webtoon modes, zoom, the seamless next chapter, and the reader settings), and the library features [Phase 6](../docs/phases/phase-6-library-features.md)'s (in progress: Stage 1, categories; Stage 2, history and the badges; Stage 3, the update checker and Updates; Stages 4–5, downloads; Stage 6, backup and restore).

```powershell
pnpm install
pnpm tauri dev      # run the desktop app (Vite + Rust shell); starts the backend jar
pnpm dev            # UI only, in a browser at http://localhost:1420
pnpm test           # Vitest
pnpm lint           # ESLint
pnpm format         # Prettier
pnpm typecheck      # vue-tsc
pnpm tauri build    # NSIS/MSI installer without the bundled runtime and tools: use ..\tools\build-release.ps1
cd src-tauri; cargo test; cargo clippy --all-targets   # Rust shell tests and lints
```

The routes of one kind (`/browse/:sourceId`, `/anime/:id`, `/manga/:id`, `/settings/source/:id`) go back to their section's list when the switch changes kind. ## Live check of the API operations

`src/api/__tests__/operations.live.spec.ts` runs only when `MADOYOMI_LIVE_URL` and `MADOYOMI_LIVE_TOKEN` point at a running server, e.g. one from `../tools/run-server.ps1`:

```powershell
$env:MADOYOMI_LIVE_URL = 'http://127.0.0.1:<port>'; $env:MADOYOMI_LIVE_TOKEN = '<its token>'
pnpm vitest run src/api/__tests__/operations.live.spec.ts
```

It validates every document in `src/api/operations/` against the server's schema, checks that a wrong token gets 401, checks that adding yuzono as a manga repo is refused with `REPO_TYPE_MISMATCH` and the packages (what the Repos screen's type detection relies on; it fetches the index and writes nothing), receives `extensionStoreRefreshed` through `ws.ts` after a repo refresh (that needs at least one repo), and runs a filtered search on an installed source of each kind: one filter changed through `filterChanges`, which must find entries (it needs the source's site; a source whose site fails is recorded and the next one tried, and a kind with no installed source is skipped). It also refreshes the first Popular entry of one source per kind the way the details page does, and puts it into the library and out again (an entry that was already there is put back). It changes one preference (a switch, checkbox or list) of a configurable source of each kind the way the settings page does, reads it back and restores it. Last (Phase 5), it reads a manga chapter's pages through the backend (MangaPill when installed): the first page from the source, then from the cache (and through `fetchAsset`, the token in the header), a prefetch of the next three until they are cached, and a page past the end as `NOT_FOUND`; then it saves the chapter's page, one past the end (clamped) and the read mark through `updateChapter(s)`, and puts the chapter back. Before that (Stage 5) it sets a manga's reader mode and direction in its meta, replaces the mode, reads them back with its source's name, and removes them. For each kind (Phase 6 Stage 1) it makes two categories, renames one, moves the other first, gives one a sort in its meta, puts two stored entries into both and takes them out of one, makes a third flagged for new entries and checks that an entry added to the library goes into it, then deletes all three; the kind's other categories are left as they were. For each kind (Stage 2) it saves a stored episode's or chapter's own position again, finds its entry first in the history with it, reads the library lists with their counts, and deletes that entry's history (its marks and positions stay; the rest of the history isn't touched). For each kind (Stage 3) it puts a stored entry (into the library if it wasn't) into a temporary category, checks that category for new items through `startLibraryUpdate`, follows the check to its end over the WebSocket, reads the Updates feed and the marks and clears the entry's mark, then deletes the category and puts the entry's library state back; the update settings round-trip unchanged. Run it after changing an operation or a type. Phase 6 Stage 4: it downloads a chapter of a manga source as a CBZ through the queue (pausing, moving, resuming and cancelling a second one), follows it over the WebSocket to the end, reads its pages back from the backend, and deletes the download. Stage 5: it checks ffmpeg and yt-dlp (`downloadTools`), then sets the preferred quality to 360p (put back after) and downloads the oldest episode of a Popular entry of KickAssAnime (HLS, through ffmpeg) and of AnimeGG (a direct file) through the queue, follows each over the WebSocket to the end, checks `downloaded` and `downloadCount`, and deletes it; this takes minutes. Stage 6: it round-trips the backup schedule's settings, makes a backup, reads its bytes over REST and sends them back as a picked file (a file that isn't a backup is `BAD_REQUEST`), restores it with merge followed over the WebSocket, backs up again with the same counts, and deletes the files.

## Backend sidecar

`pnpm tauri dev` starts the newest `../server/api/build/Madoyomi-Server-*.jar`, so build it once with `.\gradlew.bat :api:shadowJar` in `server/`. The shell (`src-tauri/src/sidecar.rs`):

- runs `java -jar <jar> --data-dir <dir>` with a per-session random `MADOYOMI_TOKEN`, and keeps the backend's stdin open (the backend exits when it closes);
- waits for `MADOYOMI_PORT=<port>` as long as the JVM lives (up to 5 min), then for `GET /health`, and checks `/health` every 5 s after that;
- restarts the backend after an exit or a hang, after 1, 2, 4 and 8 s, and gives up after 5 failed starts in a row (Retry in the UI);
- resolves java and the jar again for every start: a missing jar fails at once, with no restarts, and Retry looks for it again (so does a restart in a debug build, which then runs a jar rebuilt since);
- writes the backend's output, its own lifecycle lines and the UI's uncaught errors (`[ui]`) to `<data dir>/logs/sidecar.log`; Phase 7 Stage 3: it starts a new file at every app start and past 10 MB, keeping `sidecar.1.log` and `sidecar.2.log` (the backend runs in the log folder, so a JVM crash's `hs_err_pid*.log` lands there too);
- counts the backend's crashes (any run that ends without the app asking): `recentCrashes` in the last 10 minutes, `crashCount`, and `crashAlert` from 3, which brings up the UI's crash dialog (`CrashDialog`, with Export logs and Open logs folder; the failure screen has the same).

**Export logs** (Phase 7 Stage 3, `src-tauri/src/diagnostics.rs`): `export_logs` opens a save dialog (`tauri-plugin-dialog`, from Rust, so no JS package or capability) and writes a zip: `README.txt`, `about.json` (versions, the backend's state and crashes), `diagnostics.json` (the backend's `diagnostics` query, which the UI passes in when the backend answers) or else `extensions.txt` (the extensions' folders), and every `*.log`/`*.log.gz` of the log folder (the `.gz` ones unpacked). Every file is cleaned: the session's token and any `token=` value become `[token]`, the user's profile folder `%USERPROFILE%` and `USERNAME=<name>` `%USERNAME%`. `pick_folder` is the folder picker of Settings → Downloads.

Environment overrides: `MADOYOMI_SIDECAR_JAR` (jar), `MADOYOMI_JAVA` (`java.exe`; default `../tools/bin/jdk-21`), `MADOYOMI_DATA_DIR` (default `%APPDATA%\Madoyomi`).

**Release builds** (Phase 7 Stage 1) look beside the exe, in Tauri's resource dir (its `\\?\` prefix dropped): the jlink runtime in `jre/` (`../tools/jlink.ps1`), the jar as `server/Madoyomi-Server.jar`, and `mpv/`, `ffmpeg/`, `yt-dlp/` and `player/` (below). Nothing falls back to the repo, and `java` comes from PATH only when `jre/` is missing. The bundle's resources are in `src-tauri/tauri.release.conf.json`, merged with `--config` by `../tools/build-release.ps1` (which also builds the jar and the runtime and fetches the pinned tools into the gitignored `src-tauri/resources/`), so `pnpm tauri dev` and `cargo test` don't need them. `cargo test` covers where java, the jar, mpv, ffmpeg, yt-dlp and the player dir come from in both builds. The installers (Phase 7 Stage 2) are set in `src-tauri/tauri.conf.json`, since they need no binaries: `bundle.publisher` and `bundle.copyright` (also the exe's details), `bundle.windows.nsis` (per-user, `installMode: currentUser`, into `%LOCALAPPDATA%\Madoyomi`; `installerHooks: installer/hooks.nsh`, which makes the uninstaller's box remove the data dir, `MADOYOMI_DATA_DIR` or `%APPDATA%\Madoyomi`, and adds `/REMOVEDATA` for a silent uninstall; `customLanguageFiles` with `installer/English.nsh`, Tauri's English texts with that box's label changed) and `bundle.windows.wix.upgradeCode` (fixed). The version in `tauri.conf.json`, `package.json` and `Cargo.toml` is a copy of the repo's `VERSION`: change it with `..\tools\version.ps1 -Set X.Y.Z`. `tauri.release.conf.json` also bundles `LICENSE`, `NOTICE` and `THIRD_PARTY.md`, and the tools' folders whole (with their license texts).

mpv (Phase 4) is run by the backend, not the shell. Settings → Player can name the `mpv.exe` (Stage 5); it comes first. Otherwise the shell tells the backend where it is: `MADOYOMI_MPV` is passed on if set, else set to `../tools/bin/mpv/mpv.exe` when that exists (release: `resources/mpv/mpv.exe`), else left out, and the backend uses `mpv.exe` from PATH. `MADOYOMI_PLAYER_DIR` (mpv's config dir) is passed on if set, else set to `../player` (release: `resources/player`). `sidecar.log` has a `player:` line with both. The same for anime downloads (Phase 6 Stage 5): `MADOYOMI_FFMPEG` and `MADOYOMI_YTDLP` are passed on if set, else set to `../tools/bin/ffmpeg/ffmpeg.exe` and `../tools/bin/yt-dlp/yt-dlp.exe` when they exist (release: `resources/ffmpeg/ffmpeg.exe`, `resources/yt-dlp/yt-dlp.exe`), else left out (Settings → Downloads' path, then PATH); a `downloads:` line in `sidecar.log` says which. mpv is the JVM's child, so it is in the same Job Object and dies with the app.

The UI talks to it through:

| Command or event       | What it does                                                                                                                                                                                                                                                                       |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `get_backend_status`   | Status snapshot: `state` (`starting`, `healthy`, `restarting`, `failed`, `stopped`), `attempt`, `elapsedMs`, `slow`, `baseUrl`, `pid`, `serverVersion`, `error`, `exitCode`, `retryInMs`, `dataDir`, `logDir`, `seq`; Phase 7 Stage 3: `recentCrashes`, `crashCount`, `crashAlert` |
| `backend-status` event | The same snapshot, on every change and once a second while starting                                                                                                                                                                                                                |
| `get_backend_info`     | `{ baseUrl, token }` once healthy (waits while starting; the port changes after a restart, the token doesn't)                                                                                                                                                                      |
| `restart_backend`      | Retry after `failed`, or skip the backoff                                                                                                                                                                                                                                          |
| `open_backend_logs`    | Show `sidecar.log` in Explorer                                                                                                                                                                                                                                                     |
| `log_from_ui`          | Phase 7 Stage 3: a `[ui]` line in `sidecar.log` (`level`, `message`; the token taken out, cut at 4000 characters); `src/utils/uiLog.ts` sends Vue's errors, uncaught errors and rejections, 30 a minute at most                                                                    |
| `export_logs`          | Phase 7 Stage 3: the save dialog, then the zip (`diagnostics`: the backend's report or null); returns `{ path, bytes, files }`, or null when cancelled                                                                                                                             |
| `pick_folder`          | Phase 7 Stage 3: a folder picker (`title`, `start`); the folder or null                                                                                                                                                                                                            |

`src/stores/backend.ts` wraps these, and `src/components/BackendGate.vue` shows the splash, the failure screen and the restart overlay.

In plain `pnpm dev` there is no shell. Put `VITE_MADOYOMI_URL` and `VITE_MADOYOMI_TOKEN` of a server started with `../tools/run-server.ps1` into `.env.local` (gitignored) to use it from the browser.
