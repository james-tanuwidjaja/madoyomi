# Phase 6 — Library features

> Back to [PLAN.md](../PLAN.md) · Prev: [Phase 5](phase-5-manga-reader.md) · Next: [Phase 7](phase-7-packaging-release.md)

## 1. Goal

Make Madoyomi something people can live in day to day: organize the library with categories, get notified about new episodes/chapters, see history, use unread/unwatched badges, download content for offline use, and back up and restore everything. Importing Aniyomi/Mihon backups is a stretch goal.

## 2. Depends on / inputs

- Phases 3–5: library, playback progress (`episode_progress`) and reading progress (`chapter_progress`).
- `yt-dlp` and/or `ffmpeg` available in `tools/bin/` for anime downloads (bundled in Phase 7).

## 3. Deliverables

- Categories: tables, API, UI (create/rename/reorder/delete, assign entries, per-category sort).
- Update checker: scheduled job, per-category inclusion, "new" badges, WS `library.updates` event, optional Windows toast.
- History: anime and manga history list with "continue" actions and delete/clear.
- Badges: unread/unwatched counts on library cards, downloaded indicator.
- Download manager `server/core/downloads/`: queue, workers, pause/resume/retry/reorder, storage layout.
- Backup/restore: `.madoyomi-backup` (gzipped protobuf or JSON), manual + scheduled auto-backup, restore with merge.
- Stretch: import Aniyomi (`.tachibk`) / Mihon backup files.

## 4. Detailed steps

### Categories
1. Tables `category(id, type, name, order, flags)` and `entry_category`. A "Default" category always exists.
2. API: CRUD + reorder + bulk assign. UI: category tabs in Library, management dialog, multi-select assign.

### Update checker
3. Job scheduler in the backend (interval setting: off / 6h / 12h / 24h) plus a manual "update library" button.
4. For each library entry in included categories: fetch the episode/chapter list, diff it against the DB, insert new items, and mark the entry as having updates.
5. Respect source rate limits and run with limited parallelism per source; skip entries marked "completed" (setting).
6. Emit `library.updates` with counts; show an "Updates" view (new items, newest first) and an optional Windows notification through Tauri.

### History & badges
7. History is written from progress events (watched/read). The view groups entries by date and has a "resume" button.
8. Unread/unwatched counts come from a cheap aggregate query (or are cached when progress changes).

### Downloads
9. Queue model: `download(id, type, entryId, itemId, status, progress, error, order)`. Survives restarts.
10. **Manga:** fetch all pages through the image pipeline and write them to `downloads/manga/{source}/{title}/{chapter}.cbz` (with `ComicInfo.xml`).
11. **Anime:** resolve the video right before download (pick the preferred quality). For direct files, stream them with headers; for HLS, use `ffmpeg -headers … -i m3u8 -c copy` or `yt-dlp --add-header`. Save to `downloads/anime/{source}/{title}/{episode}.mkv/.mp4`, with subtitle files next to it.
12. Workers: configurable concurrency (global + per source), pause/resume/cancel/retry, reorder; progress over WS.
13. The player and reader prefer local files when they exist (mpv plays the file; the reader reads the CBZ).
14. UI: Downloads screen (queue + completed), download buttons on episode/chapter lists (single, range, "next N unread").

### Backup & restore
15. Define the backup schema: library entries, categories, progress, history, repos, extension list (not APKs), trusted certs, source preferences, app settings.
16. Create a backup manually and on a schedule (keep the last N). Restore merges or replaces, then reinstalls the listed extensions after a trust prompt.
17. Stretch: parse Aniyomi/Mihon backup protobufs and map them to our schema (sources matched by source ID).

### Tests
18. Update diff logic, download worker state machine, CBZ writer, backup round-trip (backup → wipe → restore → same state).

## 7. Risks & notes

- Update checks can hammer sources. Enforce per-source limits and stagger requests.
- HLS with expiring/encrypted segments may fail in ffmpeg. Fall back to yt-dlp and report clearly. Stage 5: ffmpeg sends the source's headers with every segment and key (an AES-128 key too), lets disguised segments through, and yt-dlp takes over when it fails, the error naming both (tested on a loopback stream; live, KickAssAnime's HLS never needed the fallback). Neither resumes: a retry or a restart downloads the stream again, so an expiring URL is resolved again for each attempt. A source can serve its audio as separate tracks (KickAssAnime does), which are downloaded beside the video.
- Backup must never include secrets in plain text where avoidable (tracker tokens come in Phase 8).

## 8. Decisions closed here

- Download tool for anime: ffmpeg, yt-dlp, or both (and which one is the default). **Decided in Stage 1 (the user's): both, ffmpeg the default.** Direct files are downloaded by the backend itself with the source's headers. HLS goes through `ffmpeg -headers … -i <m3u8> -c copy` (what Aniyomi does; it also muxes the subtitles), and through yt-dlp (`--add-header`) as the fallback when ffmpeg fails, with the failure reported. Both are bundled in Phase 7 (§9).
- Backup file format (protobuf vs. JSON) and extension. **Decided in Stage 1 (the user's): gzipped protobuf, `.madoyomi-backup`.** Upstream's and Mihon's format: upstream's manga backup (`BackupManga` with its categories, history and meta) is reused and extended with anime, repos, trusted certificates and settings, keeping the field numbers compatible so the Aniyomi/Mihon import (the stretch) stays cheap. The extension keeps it apart from a Mihon/Aniyomi `.tachibk`, which those apps would partly misread (§9).
- **Categories: one list per kind** (Stage 1, the user's; not one of the doc's two decisions, but it changes what the Library shows). Each kind's Library has its own tabs, as in Aniyomi. Upstream's manga categories stay as they are; anime gets Madoyomi's own tables (M0072, which replaces the Phase 1 stub) with upstream's rules (§9).

### Stage 5 (2026-11-16)

Decided in the stage (defaults, not asked):
- **The video is resolved right before the download**, through the extension as Play does, and picked by the player settings: the first video of the first hoster that has one in `fetchEpisodeVideos`' order (the preferred server first, then within it the preferred quality, else the source's own order). A lazy hoster is loaded when its turn comes; one that fails is skipped. A retry resolves the video again (its URL may have expired).
- **Its kind is read from the first answer**, not guessed from the URL: an `#EXTM3U` playlist or an `mpegurl` type is HLS, a `<MPD` manifest or a `dash+xml` type DASH (both to ffmpeg), anything else a file the backend streams itself through the source's own OkHttp client with the video's headers. - **HLS through `ffmpeg -c copy` into Matroska** (`.mkv`). The headers go on ffmpeg's command line (`-user_agent`, one `-headers` block), which the HLS demuxer sends with every segment and key. Segments disguised as images (`.jpg`, `.png`, common on anime sites) are let through (`-allowed_extensions ALL`, and `-allowed_segment_extensions ALL`/`-extension_picky 0` where the ffmpeg has them). **yt-dlp** takes over when ffmpeg is missing or fails (`--force-generic-extractor`, `--add-header` each, an MPEG-TS file); when both fail, the error is "ffmpeg failed: …; yt-dlp failed: …", and the queue's retries apply as for a chapter.
- **The headers on the command line are quoted for Windows** (`ProcessArgs`, the MSVCRT rules): Java's `ProcessBuilder` doesn't escape a `"` in an argument, and KickAssAnime's `sec-ch-ua` has them. Mpv's include file can't be used (ffmpeg has none), so a header value is readable by other processes of the same user while the download runs, the same user who can read the data dir; the API token never reaches a tool's environment.
- **Subtitles and external audio tracks are saved beside the file** (`<episode>.<lang>.<ext>`, `<episode>.<lang>.audio.<ext>`), not muxed: the same for a direct file and HLS, and mpv adds them as external tracks with their language as the title, chosen by the player settings' languages as when streaming. A subtitle that fails is left out (logged); an audio track that fails fails the download (the video may have no audio of its own: KickAssAnime's hasn't, found by the live check, §10). An audio track is downloaded as the video is (a file streamed, HLS through ffmpeg, else yt-dlp), its progress shown after the video's (the bar starts again for it). Muxing everything into one MKV (playable outside Madoyomi) is left for later.
- **Files:** `downloads/anime/<source (LANG)>/<title>/<scanlator_><episode>.<ext>`, upstream's file-name rule; staged in `<downloads>/.partial/anime/<episodeId>/` and moved when complete. - **The episode list's actions mirror the chapter list's:** Download per row (then its state with Cancel, Retry once failed), "Downloaded", the selection's Download and Delete downloads, and "Download…" for the next 1, 5, 10 or 25 unwatched episodes in watching order, or all unwatched. - **The format:** upstream's `Backup` fields with their numbers and models (1 manga, 2 categories, 101 sources, 9000 meta), so upstream's handlers write and read the manga part as they are, and Madoyomi's additions from field 20000 up, which Mihon (104–106), Aniyomi (500–506), TachiyomiSY (600s) and Suwayomi (9000–9002) don't use. Each app skips the fields it doesn't know. `info` (format version, app version, time, automatic) marks a Madoyomi backup; a file without it but with manga is read as a `.tachibk`.
- **What a backup holds:** both kinds' library (anime: the library entries and their seasons with every episode, its marks, position, duration and `ANIME_HISTORY` time, and the category names; manga: upstream's library manga with their chapters, history, categories, tracking and meta, which carries the per-manga reader settings), both kinds' categories with their meta (each category's sort) and flags (for manga, the "new entries", update and download flags that upstream's `BackupCategory` doesn't carry), the repos (URL, kind, format, signing key, trusted), the certificates the user trusted (USER rows; a repo's own key comes back with the repo), the installed extensions (package, kind, repo, version, signature, their sources; not the APKs), each installed source's preferences, and the backend's settings files (player, reader, library update, downloads, backups).
- **What it leaves out, and why:** the downloads and the page cache (files, re-downloadable); the download queue and the completed list (state of this install); the "new" update marks (they would show stale counts); history of entries not in the library (upstream's manga backup carries library manga only; anime does the same); the webview's localStorage (this device's: the theme, the open tab, the reader's global settings, auto-play), which a fresh install on the same Windows user keeps anyway; upstream's server and user settings (fields 9001, 9002), which hold the SOCKS proxy, login and database passwords in plain text and settings Madoyomi manages itself (`server.conf`); an extension's private preference keys (`__PRIVATE_…`, `__APP_STATE_…`, as Mihon leaves out); the schedules' anchors (a restore starts counting afresh); the API token (never stored). A source's own preferences can hold a login an extension asks for; they are carried as the extension stored them, as Mihon does (§7).
- **Files:** in `<data dir>/backups` (upstream's backup folder), `Madoyomi_<date>.madoyomi-backup` for Back up now and `Madoyomi_auto_<date>.madoyomi-backup` for the schedule; only the scheduled ones are pruned (the newest N kept), never one the user made or picked. A file is written as a `.part`, then moved. A file the user picks is sent to the backend, checked to be a backup and kept in the folder under its own name (" (2)" when taken), so every restore names a file there; the native file picker isn't needed (an `<input type="file">`).
- **The schedule:** every 24 or 168 hours from when it was turned on (the anchor kept in `backup-settings.json`, as the update check's), one that came due while the app was closed 90 s after the start; keep 1 to 50 (7). `MADOYOMI_BACKUP_INTERVAL_SECONDS` shortens it for live checks.
- **The restore dialog** checks the file first: what it holds (counts per kind), the sources its entries need that aren't installed and whether the backup's extensions bring them back, then merge or replace, the library and the settings as two boxes, and **the trust prompt**: the repos not added here (adding one trusts its signing key), the certificates not trusted here, and the extensions not installed (one no repo here or in the backup lists can't be checked), with the warning of the app's trust dialog. All of them start checked and the button says "Trust and restore" while any repo or certificate is checked: what stays checked is added, trusted or installed, nothing else.
- **The restore's order:** the settings files, the repos, the certificates, the extensions (from their repos, as the Extensions page installs them), the sources' preferences (through the extension's `SharedPreferences`), then the anime categories and entries, then the manga part through upstream's restore. A repo that doesn't answer or an extension no repo lists is a problem in the status, and the restore goes on; the entries of a source not installed come back and open once it is.
- **Merge** maps anime as upstream maps manga, by source and URL (episodes by URL): an entry missing here is added; one here keeps its fields and gains the backup's missing ones, and is in the library if either says so; a watched, bookmark or filler mark set on either side stays set; the position (and duration) is the one of the newer watch, by the history times; the history time is the later one; categories are matched by name (ignoring case), the missing ones added at the end with the backup's flags and meta, the ones here keeping their flags and gaining the meta keys they lack. Manga is upstream's merge (read or unread, the furthest page, the later read time); upstream sets a restored manga's categories to the backup's even in a merge.
- **Replace** makes the library the backup's: entries not in it leave the library (nothing is deleted from the database, so their marks come back if they are added again), categories not in it are deleted, the backup's entries' marks, positions and memberships are reset and all history cleared, then the merge above gives the backup's state, with the backup's category order, flags and meta. Repos, certificates and extensions are only ever added, and the settings are written the same way in both modes.
- **The status** (`madoyomiRestoreStatusChanged`): the step, how far it is within it (the manga's from upstream's own restore state), the entry's title, the problems, the times. One restore at a time; Settings shows it with a bar, and when it ends the app fetches everything again.
- **The Aniyomi/Mihon import (the stretch):** a Mihon or Suwayomi `.tachibk` (upstream already reads Mihon's manga) restores its manga part through the same dialog, with nothing to trust. An Aniyomi backup's anime (its fields 501–506, `BackupAnime` with sources matched by id) isn't read yet: left for Phase 8 with the trackers, or the exit run's fix round if time allows.
