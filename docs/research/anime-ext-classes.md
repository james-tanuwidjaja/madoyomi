## Key findings

1. **The declared lib version does not tell you the binary API.** AnimeGG declares lib `14`, but its bytecode calls lib-16 API: `Hoster$Companion.toHosterList(List)`, `Video.getVideoTitle()`, and the `@Deprecated(ERROR)` six-argument `Video(url, quality, videoUrl, headers, subtitleTracks, audioTracks)` constructor that was added in lib 16 for source compatibility. yuzono builds all its extensions from one tree against a current lib, and "14.x"/"16.x" is only the version-name prefix. **Do not pick an API implementation from `extensionLib`. Implement the newest surface and stay binary-compatible with the old calls.**
2. **The extensions are R8-minified.** Helper classes are named `a`…`z4`. Only the entry class and the API surface keep real names. Error logs will show obfuscated frames.
3. **Shared helpers are bundled.** `keiyoushi.utils.*` (7 classes) ships *inside* each jar. It is not something the host has to provide.
4. **`extensions-lib` is a stub jar** (`throw Exception("Stub!")`), so the host needs real implementations. Port them from the **Aniyomi app's** `source-api` (`eu.kanade.tachiyomi.animesource.*`, about 2.2k lines including docs, Apache-2.0), not from the lib. Its `Video` keeps both constructors.
5. **AnimePahe needs a WebView.** It references `android.webkit.WebView`, `WebViewClient`, `WebSettings` and `CookieManager` (very likely its DDoS-Guard/cookie solver) and `android.os.Handler/Looper`. Suwayomi's KCEF-backed WebView would cover this. A plain stub would not.
6. **The network API is the same as the manga side.** The calls go to `eu.kanade.tachiyomi.network.RequestsKt` (`GET`/`POST`), `OkHttpExtensionsKt` (`await`/`awaitSuccess`) and `NetworkHelper`, and their signatures match Suwayomi's implementation.

## API generations (aniyomiorg/extensions-lib tags)

| Change | 14 → 16 | 16 → v17 |
|---|---|---|
| `AnimeSource` | Rx `fetch*` removed; `getSeasonList`, `getHosterList(SEpisode)`, `getVideoList(Hoster)` added | popular/latest/search moved into `AnimeSource`; `getAnimeEpisodeUpdate`, `getAnimeSeasonUpdate`, `getRelatedAnimeList`, `supportsRelatedAnime` added; `getSeasonList` removed |
| `Video` | `data class Video(videoUrl, videoTitle, resolution, bitrate, headers, preferred, subtitleTracks, audioTracks, timestamps, mpvArgs, ffmpegStreamArgs, ffmpegVideoArgs, internalData, initialized)`; the old `(url, quality, videoUrl, headers, subs, audio)` constructor stays, deprecated | small changes |
| New models | `Hoster` (`hosterUrl`, `hosterName`, `videoList`, `internalData`, `lazy`; `NO_HOSTER_LIST` + `toHosterList()`), `FetchType`, `TimeStamp`/`ChapterType` | `ThumbnailInfo`, `SAnimeEpisodeUpdate`, `SAnimeSeasonUpdate`, `torrentutils.*` |

yuzono index snapshot (2026-11-03): 247 extensions, 197 with a `14.x` version name and 50 with `16.x`, none with 17.

What this means for playback (Phase 4): `Video.mpvArgs`, `timestamps` (OP/ED chapters) and `ffmpeg*Args` come from the extension. The mpv launcher should apply `mpvArgs`, and could expose `timestamps` as chapters.
